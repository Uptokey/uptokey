# Uptokey native computer tools

Native MCP stdio companion to the existing Rust/Tauri host. This package adds no model provider, model proxy, authentication service or credential store. The canonical Harness approval layer and the native window chooser remain the authorities; a tool cannot expand its window grant.

## Interface

This directory is the single canonical Rust source. Build with `cargo build --locked` from this directory. The executable is `uptokey-computer-mcp` (`.exe` on Windows). The Harness laboratory points its manifest here while retaining its existing `.local/computer-target` and isolated acceptance scripts. Canonical `prepare-sidecar.mjs` builds the native release target and includes this executable in the existing attested `resources/sidecar` bundle alongside the unchanged Node24/core runtime.

The native Harness menu resolves a content-addressed computer resource instead of the build output. `scripts/computer-resource.mjs` stages this executable and the single-source `session/` closure, hashes every file, verifies the result and atomically publishes a pointer. The Rust host embeds `resource-launcher.mjs` and uses its existing Node24 runtime to validate OS, architecture, manifest and file hashes before importing any resource module. The same verified resource serves window listing and the selected session; EOF/revocation, the original MCP client, SSH restrictions and approval policy are unchanged. Session state is separate from the immutable resource. Lab CLI entries are compatibility wrappers around these canonical sources.

The laboratory still has `bundle.active=false` and other helpers that depend on its local tree. Resource staging and canonical sidecar preparation do not establish a complete portable installer or interactive Linux/macOS acceptance. A desktop rebuild and focused Harness acceptance are separate from the static resource probe.

- `--tools-json`: prints `{tools:[...]}` without inspecting the desktop.
- `--list-windows`: local native chooser inventory `{schema:"uptokey.computer.windows.v1",platform,windows:[{id,pid,title,app,x,y,width,height,focused,minimized}]}`. This is never exposed as global inventory over MCP.
- `--window-id ID --pid PID`: immutable grant for that exact window/process, up to 15 minutes. Parent owns stdin; EOF closes the service. Closing or replacing the child revokes the grant. No grant means no capture/input.
- `--fixture` (Windows): a separate synthetic test window, used only by `acceptance.mjs`.

Seven tools: `computer_windows`, `computer_screenshot`, `computer_snapshot`, `computer_click`, `computer_type`, `computer_key`, `computer_scroll`. The windows tool only returns the granted target. All remaining tools require its exact `window_id`. Input also requires the current `observation` token. Screenshot-relative coordinates are mapped through the returned frame dimensions to native coordinates, including scaling and negative screen origins.

Every input checks target identity, visibility and foreground state. On Windows an approved input may call the normal `SetForegroundWindow` API for exactly the granted HWND/PID, then verifies the actual foreground window. This accommodates the canonical approval UI taking focus. OS refusal fails closed: there is no input attachment, privilege change, focus-lock modification or shortcut fallback. Windows also retains a live process handle and verifies the actual window under the pointer. macOS adds frontmost-window checking to XCap's application-focus predicate; X11/macOS pointer actions conservatively check observable window stacking. On those platforms the user currently brings the selected target to the foreground; automatic exact-window focus is not yet implemented. Other windows and desktop-wide capture are unavailable.

Input requires the latest one-use observation token, no older than five minutes, with the same target and geometry. Pixel equality is deliberately not an authorization condition: carets, animations and the approval UI can change pixels without invalidating the chosen target. The receipt reports the approved observation hash, a fresh pre-action hash, whether the view changed, and the post-action hash. The model must inspect the current state; these observations do not guarantee that a page/control still means the same thing. No retries or fallback clicks occur inside the helper. Cancellation is checked before dispatch and every typed character. Already-dispatched input cannot be undone by cancellation. Failed input requires recapture, because partial input can have occurred. After successful dispatch the result includes a new PNG and a `semantic_success: inspect_screenshot` receipt; a visual difference is not a claim that the user's intended task succeeded.

On macOS/X11, the MCP instructions and input-tool descriptions ask the agent to explain the manual return before requesting approval: after **Allow once**, bring the selected target window forward. The action waits up to 15 seconds; timeout sends no input. This monotonic budget starts when the approved call reaches the backend, not at a shared UI click timestamp. The call waits only for that exact existing grant, without activating any window, sending input or obtaining another approval. It checks cancellation/revocation and observation expiry between bounded 100 ms polling intervals; permission, identity, visibility and grant failures terminate immediately. A slow native enumeration cannot make a result after the deadline valid. The observation is consumed when this attempt starts: timeout/cancel requires a fresh screenshot and approval, with no recapture or retry hidden inside the helper. After the target becomes foreground, the existing frame, geometry, identity and pre-input checks still apply. This implementation is source-level only until a real macOS/X11 approval journey is accepted; the Windows handoff is unchanged.

The same macOS/X11 stdin transport marks the grant revoked on a real read EOF or read error, before the MCP library drains in-flight responses. An empty-capacity read is not mistaken for EOF. The waiting worker checks that revocation before and after native enumeration; no new listener or supervisor is introduced. Polling and cancellation cannot preempt a blocked operating-system enumeration call, but a late result is rejected without input.

Frames remain in memory, are bounded to 1600×1000/4 MiB PNG and never upscaled. Source capture is bounded to 33,177,600 pixels. Text is limited to 1024 printable characters; newline/tab must be explicit key actions. Keys are allowlisted editing/navigation keys; no arbitrary shell/eval, clipboard access or unrestricted key chord exists. Each input tool remains a potentially destructive MCP operation requiring the canonical approval policy. The process emits no tool arguments, window content or image data to logs.

`computer_snapshot` uses Windows UI Automation from the selected HWND only. It is limited to 128 nodes, depth 10 and a 3-second budget, with COM connection/transaction timeouts of 500 ms. Password controls are redacted and their children skipped; ValuePattern and clipboard are never read. Current UIA name/role/state/bounds are returned. Screenshot capture may expose visible non-password content to the selected model; this is not a promise of global zero knowledge.

## Platforms and dependencies

Maintained dependencies are pinned in Cargo.toml and transitively locked in Cargo.lock: official MCP Rust SDK `rmcp 3.8.0` (Apache-2.0), `enigo 0.6.1` (MIT), `xcap 0.9.8` (Apache-2.0), Microsoft `windows 0.62.2` (MIT/Apache-2.0). Sources: https://github.com/modelcontextprotocol/rust-sdk, https://github.com/enigo-rs/enigo, https://github.com/nashaofu/xcap, https://github.com/microsoft/windows-rs.

- Windows: actual native acceptance covers UIA tree, screenshots, click/type/submit, grant denial, stale observation denial and stdin revocation. UIPI/secure desktop restrictions are honored; no integrity changes/elevation are performed by the product.
- macOS: Enigo needs Accessibility permission and XCap needs Screen Recording permission granted through OS controls. Window capture/input code is compiled by the host's macOS build; no real macOS acceptance is claimed by Windows tests. Native accessibility tree is explicitly unavailable there in this increment.
- Linux: X11 supported by Enigo/XCap; build dependencies include pkg-config, libclang-dev, libxcb1-dev, libxrandr-dev, libdbus-1-dev, libpipewire-0.3-dev, libwayland-dev, libegl-dev, libgbm-dev and libxkbcommon-dev. A real graphical X11 session is required for native acceptance. Native accessibility tree is explicitly unavailable there in this increment.
- Wayland: refused with `wayland_window_grants_unavailable_use_x11`. Grant-scoped window enumeration/focus/input is not uniformly available across compositors; the helper does not fall back to unrestricted screen control or bypass portal permissions. This is an explicit capability limit, not a claim of complete Wayland acceptance.

`experiments/deepseek-workbench/desktop-computer/acceptance.mjs` launches only its synthetic Win32 fixture, drives it through real MCP, verifies the exact submitted canary, and terminates its own processes. Its adjacent `acceptance-output/` contains the fixture's receipt and images, never personal windows. Unit tests cover coordinates/scale, target identity/focus, stale observations and text boundaries. Full Harness/Tauri transport acceptance belongs to the parent integration. CI builds/tests the source on Windows, Ubuntu and macOS; a successful compile or package probe is not interactive OS acceptance, signing or notarization.
